Section one

Overall architecture

Three layers, one job each. The browser draws things and collects clicks. The Python server decides what is allowed and does the thinking. SQLite remembers.

What's actually installed

FastAPI
The Python web framework. It receives HTTP requests, checks the incoming JSON is the right shape, and returns JSON back. It also auto-generates the interactive docs page at /docs.
SQLAlchemy 2.0
The ORM — the translator between Python objects and SQL rows. You write db.query(Ride); it writes the SELECT.
SQLite
The database. One file on disk: ridepair.db. No separate server process to install or run.
Pydantic
Validation. Every request body and response is described as a class in backend/schemas.py, and FastAPI enforces it automatically.
PyJWT
Creates and verifies the signed login tokens.
React 19 + Vite
The frontend. Vite is the dev server and the build tool.
React Router 7
Client-side routing — the URL changes without the page reloading.
Tailwind 4
Styling, with the design tokens defined in src/index.css.

Two ways it runs

In development there are two processes. React runs on port 5173, FastAPI on 8000. The Vite config forwards anything starting with /api across to the backend: 

// frontend/vite.config.js
server: {
  proxy: { '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true } },
}

In production there is only one process. npm run build compiles React into static_react/, and FastAPI serves those files itself (backend/main.py:91).

Why this matters

Because the proxy makes API calls look like they come from the same origin, the browser never treats them as cross-origin — so CORS never causes a problem. There is CORS middleware in backend/main.py, but it's a safety net, not the thing making it work. That's a good, honest answer if a judge asks.

Section two

What happens on every single action

This exact sequence runs for every button in the app. Learn it once and you can narrate any feature.

Frontend  A component calls the API layer

A page like pages/FindRides.jsx calls api.match(query). Pages never call fetch themselves.

Frontend  One function builds the request

request() in src/lib/api.js:45 sets Content-Type: application/json, attaches the login token as Authorization: Bearer …, and converts the JavaScript object to a JSON string.

Backend  FastAPI validates before your code runs

The JSON is checked against a Pydantic class in schemas.py. Wrong type or missing field → automatic 422, and the route function is never entered.

Backend  It works out who is asking

get_current_user (backend/auth.py:64) decodes the token signature and loads that User. No valid token → 401.

Database  SQLAlchemy runs the SQL

The route reads or writes rows through a session handed to it by get_db() (backend/database.py:22).

Backend  Rows become JSON

serialize_ride() (rides.py:56) converts a database row into the exact shape declared in response_model, deciding en route what this particular viewer is allowed to see.

Frontend  React re-renders

The awaited promise resolves, the page calls setState, and React redraws only what changed.

Section three

The backend, file by file

Eight files, each with one job. If something breaks you know which one to open — that separation is itself worth saying out loud.

config.py
All the knobs in one place. College email domain, college name, the nine transit hubs with their fares and travel times, campus pickup points, vehicle types, luggage options, and the five scoring weights. Nothing else in the codebase hard-codes a hub or a fare.
database.py
Creates the SQLAlchemy engine and session factory. get_db() (line 22) hands a session to a route and always closes it, even if the route raises. init_db() (line 32) creates any missing tables at startup.
models.py
The three tables as Python classes: User (line 29), Ride (line 64), RideJoin (line 136). Also two computed properties — riders_count (line 121) and seats_filled_pct — which are derived on the fly rather than stored, so they can never go stale.
schemas.py
Thirteen Pydantic classes defining every request and response shape. This is your API contract and your first line of validation.
auth.py
Password hashing (line 30), password checking (line 40), token creation (line 55), the "who is asking" dependency (line 64), and the college-email gate (line 94).
matching.py
The algorithm. 299 lines, no HTTP anywhere in it — pure logic, which is why it's testable on its own. Five scoring functions, a match classifier, a scorer, and find_matches().
routers/users.py
Three endpoints: signup, login, me.
routers/rides.py
Six endpoints plus the serialisation helpers. The biggest file at 407 lines.
main.py
Assembles everything: creates the app, adds CORS, registers both routers, exposes /api/health and /api/meta, and serves the built React app for every non-API URL.

Why it's split this way

The rule is one reason to change per file. Adding a transit hub touches only config.py. Changing how matches rank touches only matching.py. Adding a field touches models.py and schemas.py. Nothing about HTTP leaks into the algorithm, and no SQL is written inside a route by hand.

Section five

Authentication and authorization

Two different questions. Authentication is "who are you". Authorization is "are you allowed to do this". Your code handles both, in different places.

Passwords are never stored

hash_password() (auth.py:30) generates 16 random bytes of salt, then runs PBKDF2-SHA256 over the password 120,000 times. What goes in the database is salt$hash — about 97 characters. The original password exists nowhere.

The random salt means two students with the same password still get completely different stored values, so an attacker can't spot repeats. Checking a password (verify_password, line 40) re-runs the same computation and compares with hmac.compare_digest, which takes the same amount of time whether the first character is wrong or the last — that closes a timing side-channel.

Tokens

On successful login, create_token() (line 55) builds a JWT containing the user id, email and an expiry 72 hours out, signed with the server's secret. The browser stores it and sends it on every later request.

The token is signed, not encrypted. Anyone can read its contents; nobody can change them without invalidating the signature. That's the property that matters.

The security rule that matters most

When you create a ride, the browser sends the destination, time and seats — but never who you are. The creator comes from the token: 

# backend/routers/rides.py:135
ride = Ride(
    user_id=user.id,   # from the verified token, NOT from the request body
    ...
)

If it came from the request body, anyone could post a ride in someone else's name by editing the JSON. This is the single most important line to be able to defend.

Authorization — four separate rules

  • Only verified students exist. check_college_email() (line 94) rejects any address outside the allowed domain at signup.
  • Contact details are earned. _rider_out() (rides.py:40) includes a phone number only if the viewer is on that ride and that person left sharing enabled. Everyone else literally receives null — the data never leaves the server.
  • Same-gender-only rides are invisible. Filtered out in find_matches, and independently rejected at join_ride with a 403.
  • You can't act on your own ride. Checked both in matching and in join.

Say this if asked about security

"Privacy is enforced at serialisation, not in the UI. A hidden phone number isn't hidden with CSS — the API sends null. You can open DevTools and it still isn't there."

Section six

The database

SQLite — a single file, ridepair.db. Three tables. The design decision worth defending is the third one.

users

Identity and trust: id, name, email (unique, indexed), password_hash, college, phone, gender, plus the campus identity the UI shows — class_year, major, dorm — and trust signals rating, rides_hosted, reviews_count, and the privacy flag share_contact_on_match.

rides

One table serving both "I'm offering seats" and "I need a ride", separated by the ride_type column. Alongside route and timing it stores hub_category, time_flex, seats_available, fare_total, fare_per_seat, luggage, gender_only and status.

Two storage choices are worth calling out. Departure time is stored twice: depart_time as "17:00" for display, and depart_minutes as the integer 1020 for arithmetic. "Within 45 minutes" becomes abs(a − b) <= 45 — plain integer maths instead of parsing timestamps. And the index is built to match the query that actually runs: 

# backend/models.py:115
__table_args__ = (
    Index("ix_rides_match", "ride_date", "status", "depart_minutes"),
    Index("ix_rides_hub", "to_location", "ride_date"),
)

ride_joins

The one to defend. It holds only ride_id, user_id and joined_at, with a unique constraint on the pair.

A beginner would put a passengers column on rides. That breaks immediately: one ride has many passengers, and one student joins many rides. A separate join table models a genuine many-to-many relationship — and the unique constraint means the database itself makes double-joining impossible, even if the API check were somehow bypassed.

What the database actually does, per action

ActionSQL that runs
RegisterINSERT one row into users. Unique index on email rejects duplicates.
Log inSELECT by email, then hash comparison in Python. No write.
Post a rideINSERT into rides, then an UPDATE to set the display code and increment the host's rides_hosted.
SearchReads only. One indexed SELECT plus two eager-load queries. Nothing is written — searching leaves no trace.

DashboardTwo SELECTs with eager loading, then totals computed in Python.

Honest gap

There is no Update or Delete for rides — you can't edit or cancel one yet. Create, Read and the join-write exist; the other two were cut for scope. Say that plainly if asked; it's a scope decision, not an oversight.

Section seven

The matching algorithm

This is the part that separates your project from a CRUD app, so it deserves the most rehearsal. Rides are not filtered into a list — every candidate is scored out of 100 and ranked.

One engine, three kinds of match

classify() (matching.py:139) decides what kind of pairing two rides represent:

YouThemResult
seekofferjoin_car — take a seat in their cab
seekseekgroup_up — neither of you has a car, so split one together
offerseekgive_seat — fill your empty seat
offerofferNone — two drivers have no reason to pair

The middle row is your differentiator. Most ride-share apps can only connect a rider to a driver. Yours also connects riders to each other, so four students who between them own no car still leave campus in one cab.

The formula

score = 45 × time_proximity      // how close the departures are
      + 20 × destination_match   // exact hub, or shared-word fallback
      + 15 × pickup_proximity    // same campus gate?
      + 12 × seat_fit            // does the group physically fit?
      +  8 × luggage_fit         // room for their bags?

time_proximity = max(0, 1 − Δminutes / flex_window)

Weights live in config.py and sum to exactly 100, so the score reads as a percentage.

Each of the five is a small function returning a number between 0 and 1:

_time_component
Line 84. The clever bit: the window is max(your flex, their flex) — so if either side says "±1 hour", the match is allowed. Someone flexible genuinely sees more options.
_destination_component
Line 94. Exact match scores 1.0. Otherwise it compares word overlap, so "Amritsar Station" still partially matches "Amritsar Railway Station" — that's a fuzzy fallback, not a strict equality check.
_pickup_component
Line 106. Same gate scores 1.0; a different gate still scores 0.5, because you're both on the same campus anyway.
_seat_component
Line 113. Different maths per match kind: a car needs free seats; a group needs the combined party to fit in one cab.
_luggage_component
Line 127. Luggage is ranked, not compared for equality — a ride that allows suitcases also allows backpacks, so it compares ranks.

How the search runs

find_matches() (matching.py:235) is deliberately two-phase:

  • Phase one — the database does the cheap work. One indexed SELECT narrows to the same date, still open, not your own ride, inside the widest possible time window.
  • Phase two — Python does the expensive work on the handful that survived: safety filters, then scoring.
  • Finally results.sort(key=lambda r: (-r["score"], r["time_gap_minutes"])) — best score first, ties broken by whoever leaves closest to your time.

That ordering is the scalability argument: scoring never runs over the whole table, only over what's plausibly relevant.

Section eight

How the frontend talks to the backend

Every network call in the entire app goes through one function. That's the design decision to lead with here.

The single door

// frontend/src/lib/api.js:45
async function request(method, path, body) {
  const headers = { 'Content-Type': 'application/json' }
  const token = getToken()
  if (token) headers.Authorization = `Bearer ${token}`

  res = await fetch(path, {
    method, headers,
    body: body === undefined ? undefined : JSON.stringify(body),
  })

  // session died — bounce to login, once, centrally
  if (res.status === 401 && token) {
    clearSession()
    window.dispatchEvent(new CustomEvent('ridepair:logout'))
    throw new ApiError('Your session expired. Please log in again.', 401)
  }
  ...
}

Because the token is attached in exactly one place, no page can ever forget it. Because expiry is handled in one place, every screen logs out correctly. And because non-2xx responses are converted into a thrown ApiError with the server's own message, every screen can just write catch (err) → toast(err.message).

Underneath, the endpoints are one line each — api.js:89–100:

signup:  (p) => request('POST', '/api/auth/signup', p),

Where the login state lives

context/AuthContext.jsx holds the current user for the whole app. On first load it reads the stored user so the screen doesn't flash, then calls api.me() to confirm the token is still genuinely valid — if not, it clears the session. Protected routes in src/App.jsx read that state and redirect to /auth when nobody is logged in.

Be precise about this one

That redirect is convenience, not security. The real protection is server-side: every protected route declares Depends(get_current_user). Even if someone edited the JavaScript to show the dashboard, the API would return 401 and there'd be no data to show.

Section nine

Two complete traces

Learn these two and you can answer almost any "walk me through it" question.

Trace A — searching for a ride

You submit the search form

FindRides.jsx builds a query object and calls api.match(q) at line 62.

The request goes out

POST /api/rides/match with a JSON body and Authorization: Bearer …. Skeleton loaders appear immediately.

Pydantic validates

The body is checked against MatchQuery (schemas.py:121). depart_time must match the regex ^\d{2}:\d{2}$.

The token is decoded

get_current_user turns the token into a real User object.

One indexed SELECT

Same date, status open, not your own ride, departure inside the window. joinedload and selectinload pull each ride's host and passengers in the same trip.

Scoring in Python

Safety filters drop gender-restricted rides; survivors are scored by the five components; anything under 35 is discarded; the rest are sorted.

Rows become JSON

serialize_ride runs per match — and sets every phone to null, because you haven't joined yet.

React renders the board

setMatches(...) replaces the skeletons with ranked cards, each able to show its own score breakdown.

Measured at 20,000 rides: 24 ms median, end to end over HTTP.

Trace B — joining a ride

You press "Request to Join"

join(rideId) at FindRides.jsx:96 calls api.join(rideId).

POST /api/rides/{id}/join

No body at all — the ride comes from the URL, and you come from the token.

Six guards run in order

Ride exists · not your own · still open · seats remain · gender rule satisfied · not already joined. Each failure returns a specific message, not a generic error.

One transaction

INSERT the join row, decrement seats_available, flip status to full at zero, recalculate the per-head fare, then a single commit(). Either all of it happens or none of it does.

Serialisation now decides differently

Because you're on the ride, _rider_out now includes the phone numbers. Same function, different output, driven by who's asking.

The UI updates

A success toast fires and the card is removed from the board, because that match is no longer available to you.

# backend/routers/rides.py:384 — the whole transaction
db.add(RideJoin(ride_id=ride.id, user_id=user.id))
ride.seats_available -= 1
if ride.seats_available == 0:
    ride.status = "full"
db.flush()
_recalculate_fare(ride)
db.commit()   # all of it, or none of it
Section ten

Concepts you can genuinely claim

Every item here is actually in your code. Nothing aspirational.

REST API design
Ten endpoints, resource-shaped URLs, correct verbs, correct status codes (201 created, 400 bad request, 401 unauthorised, 403 forbidden, 404 missing, 422 validation).
Stateless JWT auth
Signed tokens with expiry; no server-side session store, which is exactly what lets the API scale horizontally.
Password security
PBKDF2-SHA256, 120,000 iterations, per-user random salt, constant-time comparison.
Authorization rules
Domain-restricted registration, conditional field disclosure, gender-restricted visibility enforced in two independent places.
Relational design
Three normalised tables, a proper many-to-many join table, foreign keys, a unique constraint, cascade deletes, composite indexes chosen to match the real query.
A ranking algorithm
Five weighted components summing to 100, an asymmetric flexibility window, fuzzy string matching, ranked ordering with tie-breaks — and a returned breakdown that makes it auditable.
Transactional integrity
Seat allocation as one atomic unit; a database-level unique constraint as the backstop.
Declarative validation
Pydantic schemas with type, length, range and regex rules that run before any route code.
Dependency injection
FastAPI's Depends() supplies the DB session and current user, so routes never manage either manually — and the session always closes.
Query optimisation
Eager loading to remove an N+1 (110 queries → 3) and aggregate SQL replacing an in-Python loop (3,813 ms → 57 ms), both measured.
Async request handling
Every frontend call is a promise with proper loading, success and error states; the UI never blocks.
Config-driven design
Hubs, fares, weights and rules live in one file; adding a destination needs zero code changes anywhere else.
Automated testing
npm run smoke mounts all seven routes against the live API in jsdom and fails if any screen crashes or loses its content.
Section eleven

The judge's view

Genuinely impressive

  • The score breakdown. Plenty of teams claim an algorithm; you can show the points each component contributed, live, on any card.
  • Seek-to-seek matching. A real product insight, not just a feature — it serves the students who have no car at all.
  • The measured optimisation. Finding your own N+1 and your own O(n) landing page, then fixing both with numbers to prove it, is senior-engineer behaviour.
  • Privacy enforced server-side. Field-level disclosure based on relationship, not CSS.
  • The asymmetric time window. A subtle, thoughtful rule most people wouldn't think of.

Honestly simple

Worth admitting freely — it builds credibility. The CRUD endpoints are standard. There's no GPS, maps, payments or real-time anything. The CO₂ figure is a flat multiplier, not a real emissions model. Ratings display but nothing writes to them yet. Scoring weights were chosen by judgement, not trained on data.

What they'll probe — and your answers

"Why not just filter?"
Filtering gives a list with no order. Ranking answers "which of these is best for me" — and time proximity matters more than pickup point, which a filter can't express.
"Where did the weights come from?"
Judgement: departure time is the thing that actually makes a shared cab work. They're constants in config.py, so they're tunable — and with real usage data they'd be learned rather than assumed.
"Does it scale?"
Tested at 20,000 rides: 24 ms matching. Scoring runs only on candidates inside the time window, not the whole table. SQLite→Postgres is one line; auth is stateless so the API scales horizontally.
"What if two people take the last seat?"
Today it's one transaction, and SQLite has a single writer, so it holds. On Postgres you'd add SELECT … FOR UPDATE — three lines. Know this one; it's the sharpest question they can ask.
"Is JWT in localStorage safe?"
It's vulnerable to XSS. Production would use httpOnly cookies. For a campus MVP with no untrusted user-generated HTML, it's an accepted trade-off.
"How do you know it works?"
A smoke test mounts every route against the live API and fails on any crash or missing content.

Weaknesses to own before they're found

No rate limiting on login. No email verification — the domain check trusts the address. No edit or cancel for rides. SECRET_KEY is committed in config.py and would need to move to an environment variable. Naming each of these before a judge does turns a weakness into evidence that you understand your own system.

Section twelve

The ten things to know cold

If you only rehearse one section, rehearse this one. Each has a line you can actually say.

  1. The three-layer round trip

    Browser → api.js attaches the token → FastAPI validates → token identifies you → SQLAlchemy queries SQLite → rows serialised to JSON → React re-renders.

    "Every action in the app follows the same seven steps."

  2. The scoring formula

    45 time, 20 destination, 15 pickup, 12 seats, 8 luggage — summing to 100. Memorise these five numbers.

    "We don't filter rides, we score them out of 100 and rank them."

  3. Three match types from one engine

    join_car, group_up, give_seat — decided by classify() in matching.py.

    "Other apps match riders to drivers. We also match riders to each other."

  4. The creator comes from the token

    user_id=user.id in create_ride — never from the request body.

    "The browser can lie about anything, so identity always comes from the signed token."

  5. Passwords are hashed, never stored

    PBKDF2-SHA256, 120,000 iterations, random per-user salt, constant-time comparison.

    "Even with the database file, you can't recover anyone's password."

  6. Why ride_joins is its own table

    Many-to-many: one ride, many passengers; one student, many rides. Unique constraint on the pair.

    "A passengers column would have broken the moment a second person joined."

  7. Time stored as minutes since midnight

    "17:00" for display, 1020 for maths.

    "Comparing departure times is integer arithmetic, so the window check is trivial and fast."

  8. Joining is one transaction

    Insert the join row and decrement the seat together; commit once.

    "A seat can never be sold twice or go negative — it's all-or-nothing."

  9. Privacy is enforced at serialisation

    _rider_out() returns phone=None unless you're on the ride and sharing is on.

    "The number isn't hidden in the UI — the API never sends it."

  10. The measured performance story

    20,000 rides: matching 24 ms. Found and fixed an N+1 (110 → 3 queries) and an O(n) landing page (3,813 ms → 57 ms).

    "We profiled it, found two bottlenecks, and fixed both — here are the numbers."
